# AGENTS.md —— trade 工程开发规范

> 本文件面向所有编码 Agent（Claude Code、Cursor、Codex、Cline、Copilot、Kiro 等）和人类开发者，是本仓库的**最高优先级工程规范**。与设计文档冲突时：工程规范以本文为准，业务规则以 `docs/` 为准。
> 工具若只识别自己的文件名（如 `CLAUDE.md`、`.cursorrules`、`.github/copilot-instructions.md`），只需在其中写一行“请遵循仓库根目录 AGENTS.md”。

## 1. 项目速览

- 是什么：币安山寨币分钟级超短线**只做多**量化工具。PyTorch 模型识别突破 → Walk-Forward 回测 → 测试网 → 影子盘 → 小资金实盘。
- 设计文档入口：`docs/design.md`（索引）→ `docs/01`~`docs/10`。**动手前先读与任务相关的章节。**
- 数据与交易全部基于币安（`docs/09`）；币安接口以 developers.binance.com 最新文档为准，与设计文档不一致时先报告再改。
- 语言与环境：Python 3.11+（本地 3.13 为主，服务器用发行版 Python）；本地 Windows（研究/训练，CUDA），Ubuntu 实盘服务器（实盘，CPU）；看板为 Streamlit 网页（服务器部署，经 Caddy HTTPS 供电脑与手机访问）。本地在中国大陆、不开 VPN，不直连币安（`docs/02` §5）。
- 规模：个人小工具。追求正确、可读、可验证，不追求框架化。**不要引入设计文档之外的新模块、新抽象层、新依赖**，确需引入时先说明理由。

## 2. 每次任务的工作流程

1. **读**：读任务相关的设计章节和将要修改的现有代码。不读不改。
2. **对齐**：发现设计文档缺失、矛盾或与真实接口（如币安 API 变更）不符时，先列出问题与建议方案。影响交易结果、风险或资金安全的问题必须停下来问使用者；只影响实现细节的可以按建议方案继续，并在完成报告中写明。
3. **改**：小步修改，一次只做任务范围内的事。不顺手重构无关代码。
4. **同步文档**：按 §5 检查并更新文档。
5. **验**：运行 §8 的质量检查命令，全部通过。
6. **报**：按 §9 写中文完成报告。

## 3. 代码规范

### 3.1 基本

- 格式与 lint：`ruff format` + `ruff check`（规则集至少 `E,F,W,I,B,UP,N,SIM`，行宽 100）。
- 类型：所有公开函数写完整类型注解；`trade.common`、`trade.backtest`、`trade.live` 必须通过 `mypy --strict`（可对第三方库缺失存根做局部忽略，需注释原因）。
- 命名：模块/函数/变量 `snake_case`，类 `PascalCase`，常量 `UPPER_SNAKE`。特征名、配置键与设计文档中的名称**完全一致**（如 `cvd_norm`、`position_frac`），便于全文检索对照。
- 函数长度建议 ≤ 60 行，超过时拆分；单文件建议 ≤ 500 行。
- 禁止：`print`（脚本的最终结果输出除外）、通配导入、可变默认参数、裸 `except:`、在库代码里调用 `sys.exit`。

### 3.2 本项目强制约定

| 主题     | 规则                                                                                                               |
| :------- | :----------------------------------------------------------------------------------------------------------------- |
| 时间     | 一律 UTC、`int64` 毫秒时间戳；变量名以 `_ms` 结尾（如 `open_time_ms`）。禁止使用本地时区和 naive `datetime` 做计算 |
| 路径     | 一律 `pathlib.Path`；路径根来自配置 `paths`，禁止硬编码绝对路径                                                    |
| 数值     | 价格、数量在下单前必须经 `tickSize`/`stepSize` 取整函数处理；金额比较使用容差，不用 `==`                           |
| 魔法数字 | 阈值、费率、窗口长度全部来自配置；代码内常量须命名并注释出处（设计文档章节）                                       |
| 配置     | 新增配置项必须同时：加入 pydantic 模型（含范围校验）、加入对应 `configs/*.yaml` 示例、更新设计文档                 |
| 随机性   | 需要随机的地方显式传入 `np.random.Generator` 或种子，不使用全局随机状态                                            |
| 异常     | 离线流程失败即抛出（带币种、时间、文件等上下文）；实盘流程按 07 进入安全模式，不吞异常                             |
| 日志     | 使用 `trade.common.logging`，结构化字段；禁止输出密钥、签名、Webhook 完整地址                                      |
| 依赖     | 新依赖需锁定精确版本写入对应 `requirements-*.lock`（base/research/live，见 02 §4），并在完成报告说明用途；优先标准库与已有依赖 |
| 性能     | 先写正确的版本并有测试，再优化；numba 函数必须有对应的纯 Python 参考实现用于测试比对                               |

## 4. 注释与文档字符串规范

- 注释语言：**中文**。标识符、API 名称、专有名词保持英文。
- 每个模块文件开头写模块文档字符串：一句话职责 + 对应设计章节。例：

```python
"""三重障碍标签计算。

规格：docs/04-特征与标签.md §7
"""
```

- 公开函数/类使用 Google 风格 docstring（中文），必须写明：用途、参数（含单位，如“毫秒”“比例，0.01 = 1%”）、返回值、可能抛出的异常。实现了设计公式的，写明“见 04 §4.1 #12”。

```python
def calc_notional(base_amount: float, sl: float, cfg: SizingConfig, ...) -> SizingResult:
    """按仓位配置计算单笔名义价值。

    规格：docs/06-回测引擎.md §5（回测与实盘共用，禁止另写一份）。

    Args:
        base_amount: 资金基准 B，USDT。
        sl: 止损幅度，比例（0.008 = 0.8%）。
        cfg: 仓位配置，见 06 §5.4。

    Returns:
        SizingResult，含 notional（USDT）与 capped_by（截断原因，未截断为 None）。

    Raises:
        ConfigError: 配置未通过 06 §5.4 校验。
    """
```

- 行内注释写“为什么”，不写“做了什么”。重点注释：防未来函数的处理、保守假设（如同根 K 线先判止损）、交易所接口的坑、与设计文档的有意偏差。
- 与设计文档有意偏差时，必须写 `# NOTE(偏差): 原因 ... 已同步 docs/xx §y`。
- 待办统一格式：`# TODO(YYYY-MM-DD): 内容`，完成报告中列出新增的 TODO。
- 删除代码就删干净，不保留注释掉的旧代码。

## 5. 文档同步规则（改代码必查）

**原则：设计文档描述的是“当前真实行为”。** 代码行为变化而文档未改，视为任务未完成。

### 5.2 同步方式

- 直接修改对应章节正文，不要在文末追加“补充说明”。
- 涉及跨文档的规则（如 06 §3 与 07 §5），两处都改，并互相引用章节号。
- 实质性修改（影响行为、阈值、接口）在 `docs/design.md` 的“文档变更记录”追加一行。
- 修改后检查：章节号引用是否仍正确、配置示例与 pydantic 模型字段是否一致。

## 6. 量化专项红线（违反任一条，任务视为失败）

1. **无未来函数**：t 时刻只用 t 及以前已知的信息；入场价用延迟后的逐笔价 `p_1s(t+1)`（06 §3.2）；执行类原子量不得作为特征；归一化只用历史统计量；出场策略状态只在 K 线收盘更新、下一根生效。新增特征必须通过未来函数测试（08 §2 P2）。
2. **封存集不可碰**：开发中不得加载 M23~M24 数据，不得用 `--final` 以外的方式评估封存集，不得根据封存集结果调参。
3. **测试段不可调参**：超参、出场策略与标签参数只能在调参期（M1~M12）选择；阈值只能在各折验证集上选择；每次测试段回测登记 `EXPERIMENTS.log`。
4. **单一实现**：特征计算（`trade.features`）、仓位计算（`trade.common.sizing`）、出场策略（`trade.common.exits`）、交易规则取整在回测与实盘中共用同一份代码。
5. **回测实盘一致**：改了其中一边的成交/风控规则，另一边必须同步或在文档中明确说明为何不需要（07 §7.1 “回测是否模拟”列）。
6. **名单不可擅改**：训练与回测评估币种只能来自使用者确认的 `configs/coins.yaml`，且必须通过 `select_coins.py --validate`；Agent 不得增删币种或调换训练/留出角色；盲测币抽取后不得重抽。实盘候选池为动态涨幅榜前 20（07 §3.5），与 `coins.yaml` 固定名单无关，但不得因候选池动态化而放宽风控或闸门。
7. **不放宽风控与闸门**：Agent 不得自行修改风控默认阈值、闸门标准、`--i-understand-the-risk` 确认机制；仓位比例等参数只能由使用者设定。
8. **密钥安全**：密钥只来自环境变量；不写入代码、配置、日志、测试、报告、通知消息（WxPusher 等第三方会看到消息内容）；API Key 不开提现权限。
9. **实盘安全**：任何改动不得造成“有仓位无止损”的窗口；止损先于止盈挂出；订单请求状态未知时先查询再重发。
10. **不伪造结果**：报告中的数字必须来自实际运行输出，未运行的写“未运行”及原因。
11. **不加规避访问限制的功能**：不实现把本地币安请求转发出去的代理、隧道等代码或配置（02 §5.3）；凡需访问币安的步骤只在东京服务器上执行。看板的 Caddy HTTPS 入口不转发币安流量，不属于此类。
12. **看板安全**：Streamlit 只监听 `127.0.0.1`，公网入口只能是带认证的 Caddy；控制操作必须经 `trade.live.control` 与 PIN 二次确认；看板不得提供清除停机标志、切换运行模式的功能（10 §3.5、§5）。
13. **改单无空窗**：追踪止损改单必须先挂新单、确认成功后再撤旧单（07 §5.2）。

## 7. 测试规范

- 框架 pytest，`tests/` 结构与 `src/trade/` 一一对应，文件名 `test_<模块>.py`。
- 每个 bug 修复附带一个能复现该 bug 的测试。
- 测试数据放 `tests/fixtures/`，手工构造、体积小；依赖真实下载数据的测试标记 `@pytest.mark.data`，网络测试标记 `@pytest.mark.network`，默认均不运行。
- 测试用例命名表达场景：`test_同根K线同时触发止盈止损时按止损计`（允许中文函数名，或使用英文 + 中文 docstring，二选一，同一文件内保持一致）。
- 08 §4 列出的关键测试必须存在且通过。

## 8. 质量检查命令

完成任务前在仓库根目录执行，全部通过才能写完成报告：

```text
ruff format --check .
ruff check .
mypy --strict src/trade/common src/trade/backtest src/trade/live
mypy src/trade/dashboard
pytest -q
```

涉及数据、训练、回测的任务，另需运行相关脚本的最小规模版本（如 1 个币 × 3 天）并在报告中附关键输出。

## 9. Git 规范

- 分支：`feat/<阶段>-<简述>`、`fix/<简述>`、`docs/<简述>`。不直接提交到 `main`。
- 提交信息：`<类型>(<模块>): <中文简述>`，类型为 `feat|fix|refactor|test|docs|chore|perf`。例：`feat(labels): 实现三重障碍标签`。
- 代码与其对应的文档修改放在同一个提交。
- 禁止提交：`data/`、`artifacts/`、`.env`、任何密钥、大于 1 MB 的文件。`.gitignore` 需覆盖这些路径。
- 只在使用者要求时提交或推送；不使用 `--force`、`--no-verify`。

## 10. 完成报告

每次任务结束后，按 `docs/reports/TEMPLATE.md` 写中文报告，保存为 `docs/reports/YYYYMMDD-<阶段或简述>.md`（同日多份加序号 `-2`）。同时在对话中给出 3~5 句话的摘要和报告路径。

报告要点：做了什么、改了哪些文件、文档同步情况、验证结果（命令与输出摘要）、与设计的偏差、遗留问题与需要使用者决定的事项。**不夸大，未验证的明确写未验证。**
