# 03 数据与选币

## 1. 数据源

全部使用币安官方公开数据，无需 API Key。**下载与聚合在东京服务器上执行**（02 §5.2），本地只接收聚合后的分钟数据。币安数据与接口总说明见 [09-币安数据与API.md](./09-币安数据与API.md)。

| 数据                  | 来源                                                                | 粒度   | 用途                                                                 | 必需 |
| :-------------------- | :------------------------------------------------------------------ | :----- | :------------------------------------------------------------------- | :--- |
| 交易规则 exchangeInfo | REST `/fapi/v1/exchangeInfo`                                        | 快照   | 合约列表、上线时间 `onboardDate`、`tickSize`/`stepSize`/最小名义价值 | 是   |
| 日线 K 线（全市场）   | data.binance.vision `data/futures/um/monthly/klines/{SYMBOL}/1d/`   | 1 天   | 选币第一阶段：上线时长与成交额排名（§4.2）                           | 是   |
| 1m K 线 klines        | data.binance.vision `data/futures/um/monthly/klines/{SYMBOL}/1m/`   | 1 分钟 | 主特征、标签、回测成交                                               | 是   |
| 归集逐笔 aggTrades    | data.binance.vision `data/futures/um/daily/aggTrades/{SYMBOL}/`     | 逐笔   | 订单流特征、**入场延迟价与入场后高低点**（§2.2）                     | 是   |
| 合约指标 metrics      | data.binance.vision `data/futures/um/daily/metrics/{SYMBOL}/`       | 5 分钟 | 持仓量变化、多空比                                                   | 否   |
| 资金费率 fundingRate  | data.binance.vision `data/futures/um/monthly/fundingRate/{SYMBOL}/` | 每期   | 回测资金费成本、可选特征                                             | 是   |
| BTCUSDT 1m K 线       | 同 klines                                                           | 1 分钟 | 市场环境特征                                                         | 是   |

### 1.1 已知数据格式陷阱（实现时必须处理）

1. **CSV 表头不统一**：部分较新的文件第一行是表头，较旧的没有。读取时检测首行是否为数字。
2. **时间戳单位**：合约为毫秒；为防将来变更，统一规则：值 > 1e14 视为微秒，除以 1000 转为毫秒。
3. **月度文件与日度文件**：当月数据只有日度文件。下载器优先月度，缺失月份用日度补齐。
4. **校验和**：每个 zip 都有同名 `.CHECKSUM` 文件（SHA256），下载后必须校验，失败重试 3 次后报错。
5. **倍数合约**：如 `1000PEPEUSDT` 价格与数量单位与现货不同。特征只使用比例类量，不受影响；报告中显示原合约名。
6. **缺失分钟**：缺失 K 线时价格 OHLC 用上一收盘价填充、成交量填 0，带 `is_filled = 1` 标记，并在质量报告中统计。`is_filled` 的分钟**不产生样本、不允许开仓**。
7. **中文交易对名**（如 `龙虾USDT`）：URL 中需百分号编码；本地文件路径、`newClientOrderId`、日志键名一律使用 ASCII 别名（`alias`，如 `C014`，由 §4.5 的 `aliases.json` 统一分配），避免 Windows 路径编码与交易所 ID 字符集问题。WebSocket 流名称的写法以官方文档为准，P1 用 `api_smoke.py` 实测。
8. **成交口径一致性**：确认历史 aggTrades 与实时 `@aggTrade` 流的成交口径一致（例如是否包含某些特殊订单类型的成交）。P1 用一天的实时录制与次日的历史文件逐条比对，差异写入质量报告。

### 1.2 K 线字段（12 列）

`open_time, open, high, low, close, volume, close_time, quote_volume, count, taker_buy_volume, taker_buy_quote_volume, ignore`

### 1.3 aggTrades 字段（7 列）

`agg_trade_id, price, quantity, first_trade_id, last_trade_id, transact_time, is_buyer_maker`

`is_buyer_maker = true` 表示买方是挂单方，即**主动卖出**；`false` 为**主动买入**。这是最常见的方向理解错误，必须写单测。

## 2. 下载与存储

### 2.1 下载器 `trade.data.downloader`（服务器运行）

- 输入：`symbols`、`data_types`、月份范围。下载范围由 §4.2 决定：全市场只下载日线；1m K 线、aggTrades、metrics、fundingRate 只下载**至少入选过一次**的币，范围为其每段入选期及之前 30 天预热，再多下载 1 天（用于计算第一天的大单阈值，§2.2）。
- 断点续传：目标 zip 已存在且校验通过则跳过；已聚合完成的“币·日”记录在 `data/raw/_done.parquet`，重跑时跳过。
- 单文件失败指数退避重试（1s、2s、4s），3 次后记录到失败清单并继续下一个，不中断整批任务；失败清单在批次结束时重试一轮并写入报告。
- 输出：`data/raw/{type}/{alias}/{文件名}.zip`（aggTrades 聚合后立即删除）。

**任务清单与优先级。** 先完成全市场日线与 §4 的 24 个月快照，再由快照生成精确的 `(币, 日)` 任务清单 `data/raw/_jobs.parquet`，按以下顺序处理：

1. 调参期 M1~M12（及其预热），同一阶段内入选月数多的币优先；
2. 测试段 M13~M22；
3. 封存集 M23~M24（只聚合，开发期间不加载，08 §3 G3）。

每个阶段完成后同步到本地（§2.3），本地即可开始该阶段可做的工作（08 §2 P2/P3：调参期数据到位后先用 R0 检查毛期望）。

**并发模型（按 2 vCPU / 3.6 GB 内存 / 30 Mbps 设计）。** 2 个聚合进程，每个进程负责一个币、按日期顺序处理；每个进程带 1 个下载线程，预取后 2 天的文件（下载与解析重叠）。在途 zip 总量 ≤ 2 GB，避免占满磁盘。30 Mbps 下下载通常是瓶颈，不需要更多进程。

### 2.2 聚合 `trade.data.aggregate`（服务器运行）

aggTrades 体积很大，**不保存解压后的原始逐笔**，按日流水线处理：下载一天 → 校验 → 聚合 → 删除该日 zip（`keep_raw_aggtrades: false`；S8 需要的 3 币 × 1 月例外）。

**大单阈值规则。** 对每个币每个 UTC 日 D，计算当日全部归集成交单笔成交额（`price × quantity`）的 99 分位数 `p99(D)`，写入 `data/bars/{alias}/whale_thr.parquet`（`date`、`p99_quote`、`n_trades`）。**第 D 日使用的大单阈值 `whale_thr(D) = p99(D-1)`**，只用前一天。

**单遍处理。** 同一币按日期升序处理，读第 D 日文件时一次完成两件事：用已算好的 `p99(D-1)` 计算第 D 日的分钟原子量，同时计算 `p99(D)` 留给第 D+1 日。每个文件只解析一次。第一段数据的首日只用于计算 `p99`，不产出分钟数据。若某日文件缺失，次日的阈值沿用最近一个可得的 `p99` 并在质量报告中记录。**计算口径与旧的两遍实现完全相同**，由等价测试保证（08 §2 P1）。

**读取与汇总。** 用 `pyarrow.csv.open_csv` 流式读取（块大小 32 MB，显式列类型，只读 `price, quantity, transact_time, is_buyer_maker` 4 列；兼容有无表头、`is_buyer_maker` 的 `true/True` 写法、毫秒/微秒时间戳，§1.1）；按 `transact_time // 60000 * 60000` 归入分钟，用 numba 函数做分钟内的求和、最大、最小与“最后一个”；跨块的同一分钟合并。单进程内存峰值目标 < 1.5 GB，与文件大小无关。`p99(D)` 需要全天成交额：只保留 `price × quantity` 一列（float64），按块收集后精确求分位数；单日 5000 万条约 400 MB，仍在内存目标内。**不使用近似分位数**，以免改变计算口径；基准测试记录热门币单日的峰值内存。numba 函数需有纯 Python 参考实现用于测试（AGENTS.md §3.2）。

| 字段                        | 含义                                                                                                                                     |
| :-------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------- |
| `open_time`                 | 分钟起点（毫秒）                                                                                                                         |
| `agg_n`                     | 归集成交条数                                                                                                                             |
| `buy_quote` / `sell_quote`  | 主动买 / 主动卖成交额（USDT）                                                                                                            |
| `max_trade_quote`           | 本分钟最大单笔成交额                                                                                                                     |
| `max_buy_1s_quote`          | 本分钟内任一秒的主动买成交额合计的最大值                                                                                                 |
| `whale_buy_quote`           | 单笔成交额 ≥ `whale_thr(D)` 的主动买成交额                                                                                               |
| `whale_sell_quote`          | 单笔成交额 ≥ `whale_thr(D)` 的主动卖成交额                                                                                               |
| `whale_thr`                 | 本分钟所用的大单阈值（便于审计）                                                                                                         |
| `p_1s` / `p_3s`             | **入场延迟价**：`transact_time ≤ open_time + 1000`（或 3000）ms 的最后一笔成交价；该区间无成交时取上一分钟收盘价，并置 `p_1s_filled = 1` |
| `hi_post_1s` / `lo_post_1s` | **入场后高低点**：`transact_time > open_time + 1000` ms 且在本分钟内的成交价最高 / 最低；无成交时等于 `p_1s`                             |
| `hi_post_3s` / `lo_post_3s` | 同上，以 3000 ms 为界                                                                                                                    |

`p_*`、`hi_post_*`、`lo_post_*` 只用于回测成交模拟与标签（入场发生在 t+1 分钟内，属于“未来”的执行信息），**禁止作为特征**；特征注册表加载时校验特征列中不包含这些字段。

### 2.3 分钟数据文件

`data/bars/{alias}/{YYYYMM}.parquet`，一行一分钟，字段 = K 线 12 列（去掉 `ignore`）+ aggTrades 原子量 + 可选 metrics（5 分钟值，按 04 §2 规则对齐）+ fundingRate（最近一期已结算值与结算时间戳）。

- 数据类型：价格与量 `float64`，计数 `int64`。压缩：zstd。
- 按 `open_time` 严格递增、无重复，缺失分钟已补齐并带 `is_filled` 标记列。
- 同步到本地：`rsync` 增量同步 `data/bars/` 与 `data/universe/`（02 §5.8）。按 §2.1 的阶段分批：每完成一个阶段同步一次，阶段内每晚同步一次已完成的“币·月”文件；只有完整的月文件才写入（先写临时文件再改名），避免同步到写了一半的文件。

### 2.4 数据质量报告 `trade.data.quality`

每币输出：总分钟数、缺失分钟占比、最长连续缺失、零成交分钟占比、价格跳变（|1m 收益| > 20%）次数、**逐笔缺失分钟占比**（K 线有成交但 aggTrades 无记录的分钟 / 总分钟数）、aggTrades 与 K 线成交额一致性（分钟级 `buy_quote + sell_quote` 与 `quote_volume` 相对误差的中位数，应 < 1%）、§1.1 第 8 条的实时/历史口径比对结果。

**不合格判定（三条任一满足即不合格，不得用于训练或评估）**：K 线缺失分钟占比 > 1%；逐笔缺失分钟占比 > 1%；一致性误差中位数 > 2%。例如 SOLUSDT 2026-10-27 源文件缺 27 分钟：单日占比约 1.9%，放在 30 天窗口中约 0.06%，该窗口合格。逐笔缺失的分钟在 bars 组装时原子量按“无成交”填充（成交额为 0，`p_*` 取上一分钟收盘价），并置 `is_filled = 1`，因此不产生样本、不允许开仓（§1.1 第 6 条）。

**计算单位**：按“币 × 30 天窗口”计算并缓存。选币第二阶段（§4.2 第 7 步）使用 `R` 前 30 天窗口的结论；训练与评估按月使用对应窗口的结论。

## 4. 选币：规则化月度交易范围 `configs/universe.yaml`

### 4.1 方式

不使用人工固定名单。训练、回测、实盘统一使用**同一条机械选币规则**，每月初重新计算一次交易范围 `U(R)`，且每个再平衡时点 `R` **只使用 `R` 之前已知的数据**。

- **原因**：山寨币会衰亡、流动性会枯竭，固定名单不维护就会逐渐失效；人工挑选的名单又带“事后选币”偏差（多为已知涨过的币）。规则化选币免维护：新币自动进入，衰亡的币自动退出，而且回测与实盘的币种分布一致。
- **单一实现**：选币规则由 `trade.data.universe.build_universe()` 实现，离线（训练、回测）与实盘调用同一个函数（AGENTS.md §6 红线 4）。
- **规则参数由使用者确认**（`universe.yaml`），Agent 不得自行修改，也不得手工增删交易范围内的币（AGENTS.md §6 红线 6）。
- **可复现**：每个 `R` 的结果写入 `data/universe/{YYYY-MM}.json`（入选币、排名、各项指标、规则参数哈希）。同一份数据与参数重复运行，结果必须完全一致。

### 4.2 选币规则

再平衡时点 `R` = 每个 UTC 自然月 1 日 00:00。`U(R)` 在 `[R, 下个月 R)` 内有效。

**第一阶段：候选与排名（只用全市场日线 K 线与交易规则）**

| 步骤 | 规则（默认值见 §4.6）                                                                                                            | 说明                                         |
| :--- | :------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------- |
| 1    | 候选 = 截至 `R` 已上线的全部 USDⓈ-M USDT 永续，**包括之后下架的合约**（§4.4）                                                    | 包含下架合约才能避免幸存者偏差               |
| 2    | 排除：TradFi 合约（股票、商品、指数）、`BTCUSDT`（仅作市场环境）、`ETHUSDT`、稳定币对、`excluded_symbols`                        | `ETHUSDT` 不属于山寨币突破行情的目标         |
| 3    | 上线时长：`R − 首根日线时间 ≥ min_listing_days`（60 天）                                                                         | 保证 30 天预热之外还有 30 天用于判断流动性   |
| 4    | 流动性下限：`R` 前 30 天日成交额中位数 ≥ `min_daily_quote_median`（2000 万 USDT）                                                | 低流动性币点差与冲击滑点过大                 |
| 5    | 可交易性（`R` 时刻的交易规则，§4.3）：`step_notional ≤ 0.5 USDT`、`min_notional ≤ 5 USDT`、`max_leverage ≥ 5`、`tick_rel ≤ 2 bp` | 10 USDT 小本金下可下单；跳动过大则滑点不可控 |
| 6    | 排名：按 `R` 前 30 天日成交额中位数降序，取前 `top_n`（60）个                                                                    | 按成交额而不是涨幅排名，避免追涨偏差         |

- `step_notional = stepSize × R 前 7 天日收盘价中位数`；`tick_rel = tickSize / R 前 30 天日收盘价中位数`。

**第二阶段：数据质量（需要分钟数据）**

| 步骤 | 规则                                                                   | 说明                                        |
| :--- | :--------------------------------------------------------------------- | :------------------------------------------ |
| 7    | `R` 前 30 天的分钟数据按 §2.4 合格；不合格的币当月不入选，**不找替补** | 不补入第 `top_n + 1` 名，避免规则之外的挑选 |

- 已持仓的币跌出 `U(R)`：持仓按出场策略正常管理至平仓，平仓后不再开新仓（回测与实盘一致，06 §3.1、07 §3.5）。
- 某币入选当月需要的 30 天特征预热（04 §5）由第 3 步保证有数据。
- 第一阶段只需日线（数据量小）；只对**至少一次通过第一阶段**的币下载分钟级数据（§2.1），控制下载量（§3）。

### 4.3 历史交易规则的近似

data.binance.vision 没有历史 exchangeInfo，历史再平衡时点的交易规则需要近似：

| 规则           | 仍在交易的合约         | 已下架的合约                          |
| :------------- | :--------------------- | :------------------------------------ |
| `tickSize`     | 当前 exchangeInfo 快照 | 从该月 aggTrades 成交价的最小价差推断 |
| `stepSize`     | 当前 exchangeInfo 快照 | 从该月 aggTrades 成交量的最小增量推断 |
| `minNotional`  | 当前 exchangeInfo 快照 | 取 5 USDT                             |
| `max_leverage` | 当前杠杆分层快照       | 视为满足（无法得知）                  |

- 交易所会调整 `tickSize` 等规则，用当前快照近似历史是已知偏差（06 §9 A14）。它影响第 5 步的入选与回测中的取整，不影响价格数据本身。
- 实盘再平衡使用当时的 exchangeInfo 与杠杆分层，不需要近似。

### 4.4 已下架合约的数据（P1 必须先验证）

规则化选币能否消除幸存者偏差，取决于历史数据是否包含已下架合约。P1 第一步在服务器上验证：

1. data.binance.vision 是否仍保留已下架 USDⓈ-M 永续的日线、1m K 线与 aggTrades 文件；
2. 已下架合约的上线与下架时间从哪里获得（exchangeInfo 是否列出；否则以首末 K 线时间代替）。

结论写入 P1 完成报告。若下架合约数据缺失，回测仍可运行，但必须在 06 §9 A14 与报告首页注明“交易范围不含已下架合约，结果偏乐观”，并统计缺失合约的数量及其在当月排名中的位置。

### 4.5 币种角色与别名

不再由人工指定训练币与留出币，角色由规则确定，新进入的币自动分配：

| 角色     | 规则                                                                                  | 用途                                                             |
| :------- | :------------------------------------------------------------------------------------ | :--------------------------------------------------------------- |
| 留出组   | `int(sha256(symbol)[:8], 16) % holdout_mod == holdout_rem`（默认 `% 5 == 0`，约 20%） | **永不参与训练、验证、调参、阈值选择**，只在测试段与封存集上评估 |
| 训练组   | 其余币                                                                                | 训练与评估                                                       |
| 新进入组 | 评估时的派生分组：在某折测试段内入选，但在该折训练段的任何月份都未入选的币            | 检验模型对“训练时还没出现的币”的效果（06 §7 S10）                |

- 哈希规则固定，不随交易范围变化；**不得为了结果更好而更换模数或余数**（等同于挑选）。
- 别名：每个首次出现的币按出现顺序分配 `C001`、`C002`…，写入 `data/universe/aliases.json`，只增不改、不复用。离线与实盘共用同一份文件（实盘侧由服务器维护，同步回本地）。
- `BTCUSDT` 固定别名 `BTC`，只作市场环境上下文，不参与选币与交易。

## 6. 时间切分（24 个月）

记 24 个完整自然月为 M1…M24（M24 = `end_month`；按 2026-09 计，M1 = 2024-10）。预热期为 M1 之前 `warmup_days = 30` 天，只用于计算特征。

| 用途                | 月份    | 说明                                                                                 |
| :------------------ | :------ | :----------------------------------------------------------------------------------- |
| 调参期              | M1~M12  | 训练 M1~M10、验证 M11~M12，**只用于**选择超参、出场策略及其参数、标签参数（05 §6.1） |
| Walk-Forward 测试段 | M13~M22 | 5 折，每折测试 2 个月，共 10 个月样本外                                              |
| 封存集              | M23~M24 | 开发期间**禁止**加载。仅在 08 G3 执行一次最终评估                                    |

Walk-Forward 采用扩展窗口（`train.yaml: window: expanding`，可选 `rolling_12m` 作对比），超参在调参期选定后 5 折完全相同：

| 折  | 训练   | 验证（早停、校准、选阈值） | 测试    |
| :-- | :----- | :------------------------- | :------ |
| F1  | M1~M11 | M12                        | M13~M14 |
| F2  | M1~M13 | M14                        | M15~M16 |
| F3  | M1~M15 | M16                        | M17~M18 |
| F4  | M1~M17 | M18                        | M19~M20 |
| F5  | M1~M19 | M20                        | M21~M22 |

- **为什么单独设调参期**：如果用各折的验证月挑超参，F4 的验证月 M18 恰好是 F3 的测试月，测试信息就会通过超参泄露进来。调参期全部位于第一个测试月之前，彻底隔离。
- 每个边界执行 **Purge**：删除训练集末尾 `H_label` 根 K 线的样本（其标签窗口会延伸进下一段）。
- 每个边界执行 **Embargo**：再额外删除下一段开头 1 天的样本。
- 开发集结论 = 5 折测试段拼接（10 个月样本外）。
- 最终候选模型：训练 M1~M21、验证 M22，在封存集 M23~M24 上评估一次。通过后上线的就是这个模型，不再用封存集数据重训。
- **按月入选**：一个币只在它处于 `U(R)` 的月份产生样本、参与评估；不在交易范围的月份只用于特征预热。
- **数据段**：同一币的分钟数据按“连续可得区间”划分为若干段（两次入选之间间隔超过 30 天时，中间月份不下载，数据不连续）。**每段独立计算特征与 EWM 状态，段首 30 天只作预热、不产生样本**，滚动窗口不得跨越段间空档。这与实盘对新进入币只预热 30 天的做法一致（07 §3.5、04 §5）。
- 留出组的币在所有折中都不参与训练和验证，只在测试段与封存集上评估。
- 每折训练段中某训练组币的有效样本 < 60 天时，该币不计入该折训练（仍保留其评估）。
- 封存集访问控制：`loader` 的 `allow_holdout` 参数开发脚本不暴露，只有 `scripts/backtest.py --final` 可以打开，并在 `FINAL_RUNS.log` 记录执行次数。选币快照本身不含收益信息，M23~M24 的快照可以生成，但其分钟数据只能在 `--final` 时加载。
- **行情阶段差异**：24 个月跨越不同牛熊阶段，越早的数据与当前越不相似。`train.yaml: time_decay_halflife_months`（默认关闭，候选 12）作为超参在调参期评估（05 §6.1）。
