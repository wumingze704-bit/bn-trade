【第 1 步】设计书精简：去掉多余说明与修改履历，形成整洁、明确的定版设计书

背景
- docs/ 下的设计书混入了大量过程记录：带日期的实测流水（如“实测（2026-11-05，东京服务器……）”）、“已决定 / 使用者决定”的决策过程、
  09 §9 核对记录表、阶段性开发提示、多处重复解释。AGENTS.md §5.2 要求设计书“定版、自包含，只写当前真实行为与规格，不写日期、不写流水账”，现状不符合。
- 精简目标：每份设计书只回答“系统是什么、按什么规则运行、参数是多少、怎样算通过”。

范围
- 只改 docs/design.md 与 docs/01~10 的 .md 文件；新建 docs/records.md；新建 scripts/check_docs_sections.py。
- 不改 docs/tasks.md 以外的工作记录、AGENTS.md、README.md、任何代码与配置。

执行方式
- 分 4 批，每批一个聊天窗口，做完一批就停下，等使用者审阅 git diff 后再做下一批：
  批 1：design.md、01、02；批 2：03、04、05；批 3：06、07、08；批 4：09、10。
- 本次处理批次：______（下达指令时填写；未填写时 Agent 先停下询问）

必须删除或移出的内容
1. 修改履历、版本记录、“变更记录”“更新说明”“补充说明”类章节或段落：直接删除。
2. 带日期的过程描述（“2026-11-05 实测……”“截至某日……”“某日由使用者决定……”）：
   - 其中作为规格依据的数值或结论，改写成不带日期的规格句保留。
     例：“实测（2026-11-05）：algoType=CONDITIONAL + type=STOP_MARKET 可挂单” → “条件单使用 algoType=CONDITIONAL、type=STOP_MARKET”。
   - 过程本身（谁、哪天、跑了几次、原始输出）原样移到 docs/records.md，按“文档名 §章节号”分组，数字不改。
3. 09 §9“接口核对记录”整张表移到 docs/records.md；09 §9 正文只保留一句规则：
   “每次部署前按 §8 核对接口，核对记录写入 docs/records.md。”
4. “已决定 / 使用者决定 / 待使用者决定 / 方案 A、方案 B”这类决策过程：设计书只保留最终采用的规则；
   尚未决定的事项移到 docs/tasks.md 的“需要使用者决定的事项”（已有对应条目的不重复添加）。
5. 阶段性提示（例如“P5 完成之前……只覆盖组合层，报告中必须注明”）：描述当前真实行为的，改成规格语气保留；属于开发进度的，移到 docs/tasks.md 对应任务下。
6. 同一规则在多份文档里重复解释的：只在“唯一规格来源”处保留全文（仓位在 06 §5、出场在 06 §3.3、成本在 06 §4、风控在 07 §7.1），
   其他位置改成一句引用，例如“见 06 §5.2”。文档中没写明唯一来源的，不要自己定，列入完成报告由使用者决定。
7. 口语化铺垫、重复的“为什么”、与规格无关的背景介绍：删除。必要的设计理由集中保留在 design.md §6，其他文档不重复。

必须保留、不得改动（硬约束）
1. 章节编号与标题层级一律不改。代码 docstring、AGENTS.md、tasks.md 大量引用“06 §3.3”这类编号。
   某节内容全部移走时保留标题，正文写一句规格或“（本节内容见 xx §y）”。
2. 所有规格数值不改一个字符：阈值、费率、窗口长度、公式、默认参数、闸门标准、风控 R1~R14 表、特征表、配置 YAML 示例。
3. 配置示例中的键名与 configs/*.yaml、pydantic 模型保持一致。
4. 特征名、配置键名、函数名、文件路径保持原样。
5. 表格保留为表格，mermaid 图保留。
6. 精简过程中发现两份文档互相矛盾、或设计书与代码不一致：不要自己选，在完成报告里列出“文件 §章节 / 原文 / 冲突对象 / 建议”，等使用者决定。
   不得借精简修改任何规则。

验证（每批都做）
1. 新建 scripts/check_docs_sections.py（保留，以后可复用），对每份被修改的文档：
   a) 用 git show HEAD:<路径> 取修改前内容，提取全部标题行（以 # 开头），与修改后逐行比较“编号 + 标题”，必须完全一致；
   b) 提取修改前后所有数字 token（整数、小数、百分号、bp），列出“修改前有、修改后没有”的数字，
      逐个确认它们已出现在 docs/records.md（属于被移走的过程记录）；属于规格的数字一个都不能少；
   c) configs/*.yaml 的所有键名：修改前在该文档出现过的，修改后仍然出现；
   d) 全仓库（docs/、src/、scripts/、AGENTS.md）搜索“§”引用，确认被引用的“文档 §章节”仍然存在。
   脚本发现任何不一致时以非零退出码结束，输出具体行。
2. git diff --stat 只包含本批文档、docs/records.md、docs/tasks.md（若有移入）、scripts/check_docs_sections.py。

完成报告额外内容
- 每份文档修改前后的行数；移到 docs/records.md 的条目数；移到 docs/tasks.md 的条目数；
- check_docs_sections.py 的运行输出；
- 发现的矛盾清单（未处理，等使用者决定）。

执行规范
- 开始前读 AGENTS.md 与本批文档全文；第一条回复先列出本次涉及的 AGENTS.md 红线编号。
- 只做本指令范围内的修改。
- 完成后在仓库根目录运行 AGENTS.md §8 的 5 条质量命令，全部通过；按 AGENTS.md §10 用中文给完成报告，然后停止。
- 报告中的数字必须来自实际运行；没运行写“未运行”和原因。


【第 2 步】AGENTS.md 规范优化：红线合并与新增、消除矛盾表述、确立“设计书与代码一致、只写规格”

背景
- 现有红线 13 条，其中几条互相重复（4 与 5、6 与 7、9 与 13），12 条写了大量看板设计细节；§1、§1.1、§10 又重复了红线 10、11 的内容。
- 有几处表述互相矛盾，推理较弱的模型容易误读：
  * §1.1“已授权 Agent ……完成需要使用者确认的服务器操作”：既说已授权又说需要确认；
  * §1“不要引入设计文档之外的新模块、新抽象层”：与使用者下达的性能优化指令（新建脚本、新建批量内核文件）冲突；
  * §3.1“函数长度建议 ≤ 60 行”：现有代码大量函数超过 60 行，模型可能为满足此条去拆分已有函数，造成无关改动；
  * §1 写“服务器用发行版 Python”，§1.1 写“uv Python 3.13.18”，两处不一致；
  * §5“代码行为变化而文档未改，视为任务未完成”与“设计书不添加多余内容”的要求需要统一成一条明确规则。
- 审查中真实出现过、但现有红线没有覆盖的问题：缺交易规则时 tickSize 静默回退 0.01；服务器修复脚本处理到封存月；弱模型常见的“改测试断言让测试通过”；危险删除操作；性能改动可能悄悄改变结果。
- 使用者要求：设计书必须与代码一致；代码改动时同步修改设计书对应章节；同步时只写当前规格，不添加修改履历、日期、过程说明等多余内容。

范围
- 修改 AGENTS.md；把全仓库对旧红线编号的引用改成新编号（src/、scripts/、tests/、docs/ 下全部文件，含 docs/tasks.md，只替换编号，不改其他文字）。
- 不改任何代码逻辑与配置。

第一部分：用下面 15 条替换 AGENTS.md §6 的全部红线（逐字使用，不改写措辞；§6 标题与标题下第一句保留）
1. **无未来函数**：t 时刻只用 t 及以前已知的信息；入场价用延迟后的逐笔价 `p_1s(t+1)`（06 §3.2）；执行类原子量不得作为特征；归一化只用历史统计量；出场策略状态只在 K 线收盘更新、下一根生效。新增特征必须通过未来函数测试（08 §2 P2）。
2. **封存集不可碰**：开发中不得加载 M23~M24 数据，不得用 `--final` 以外的方式评估封存集，不得根据封存集结果调参。服务器上批量处理数据的脚本必须在代码中硬性限制只处理 M1~M{months−holdout_months}，不能只依赖命令行参数。
3. **测试段不可调参**：超参、出场策略与标签参数只能在调参期（M1~M12）选择；阈值只能在各折验证集上选择；每次测试段回测登记 `EXPERIMENTS.log`。
4. **单一实现、回测实盘一致**：特征计算（`trade.features`）、仓位计算（`trade.common.sizing`）、出场策略（`trade.common.exits`）、交易规则取整在回测与实盘中共用同一份代码。改了任一边的成交或风控规则，另一边必须同步，或在 07 §7.1“回测是否模拟”列写明为什么不需要。
5. **参数归使用者**：选币规则参数（`top_n`、上线天数、成交额下限等）、风控默认阈值、闸门标准、仓位比例与杠杆、`--i-understand-the-risk` 确认机制只能由使用者设定，Agent 不得自行修改。训练与回测评估币种只能来自规则化月度选币快照 `data/universe/{YYYY-MM}.json`（规则见 `configs/universe.yaml`），快照须经使用者审阅并把 `reviewed` 置 `true`；Agent 不得增删币种、不得按名单结果调规则参数、不得自行把 `reviewed` 置 `true`；哈希角色由 `sha256(symbol)` 决定，不得人工调换。实盘候选池（涨幅榜）不在回测范围内，属已知偏差，不得因此修改回测或放宽风控与闸门。
6. **密钥安全**：密钥只来自环境变量；不写入代码、配置、日志、测试、报告、通知消息（WxPusher 等第三方会看到消息内容）；API Key 不开提现权限。
7. **实盘安全**：任何改动不得造成“有仓位无止损”的窗口；止损先于止盈挂出；追踪止损改单必须先挂新单、确认成功后再撤旧单（07 §5.2）；订单请求状态未知时先查询再重发。
8. **不伪造结果**：报告中的数字必须来自实际运行输出，未运行的写“未运行”及原因；不得用 fixture 结果冒充真实数据验收。
9. **币安只在服务器访问**：凡需访问币安（REST、WebSocket、data.binance.vision）的步骤只在东京服务器执行；不实现把本地币安请求转发出去的代理、隧道等代码或配置（02 §5.3）。SSH 端口转发只把服务器上的看板端口映射到本地浏览器，不属于此类。
10. **看板安全**：看板只监听 `127.0.0.1`，不得增加任何公网入口；控制操作必须经 `trade.live.control` 与 PIN 二次确认；不得提供清除停机标志、切换运行模式的功能（10 §5.6、§9）。
11. **设计书与代码一致、只写规格**：`docs/design.md`、`docs/01`~`docs/10`、`docs/dashboard-overview.svg` 是设计书，只描述当前真实行为与规格。(a) 代码行为、配置项、接口、文件契约发生变化时，必须在同一任务内按 §5.1 对照表同步修改设计书对应章节，使设计书与代码一致；(b) 同步时只写变化后的规格（规则、公式、参数、字段、默认值），不添加修改履历、日期、实测过程、决策过程、“为什么改”的说明或补充说明段落；过程记录写入 `docs/records.md`，进度写入 `docs/tasks.md`；(c) 不修改与本次改动无关的章节，不借重构、格式化改写措辞，不改章节编号；(d) 发现设计书与代码不一致、但不属于本次任务范围时，停下报告“章节 / 原文 / 代码现状 / 建议”，不自行修改任何一边。
12. **不得篡改测试**：不得为了让测试通过而修改断言、删除测试、跳过测试（`pytest.mark.skip`、`xfail`）或放宽容差；只有使用者指令明确要求修改某个测试时才可以改，并在报告中说明改了什么、为什么。
13. **禁止静默回退**：缺数据、缺交易规则、缺配置项、缺列时直接抛出带上下文（币种、时间、文件）的异常，不得用默认值、空值或跳过的方式继续计算；实盘流程按 07 进入安全模式。
14. **危险操作先确认**：删除目录或批量删除文件（`rm -rf`、`Remove-Item -Recurse`）、删除或覆盖 `data/`、`artifacts/` 下已有文件、在服务器上删除文件或修改系统配置、重启服务、`git push --force`、`git reset --hard`、`git clean`、`git branch -D`：执行前必须列出将影响的路径或对象，获得使用者确认后再执行。
15. **提速必须等价**：以性能为目的的改动不得改变任何计算结果；必须与改动前的结果快照逐字段比对一致（整数与字符串完全相同，浮点 `rtol=1e-12`、`atol=1e-9`），不一致不算完成。

【第 4 步】回测性能：建立基准、剖析耗时、保存结果快照

背景
- 使用者实测：三个月数据的回测/调参要跑三四天，无法继续推进。
- 静态审查发现的主要耗时点（需本指令用实测确认）：
  1. src/trade/backtest/engine.py _mark_to_market_curve：
     - 对每笔交易遍历该币 close_lookup 的全部 K 线时间戳（scripts/backtest.py 加载的是从 M1 前 30 天到封存集起点的整段 bars，
       每币最多约 97 万根），复杂度 = 交易笔数 × 每币 K 线数；
     - 对每个采样时刻再遍历全部交易，复杂度 = 采样点数 × 交易笔数。两段都是纯 Python 循环。
  2. engine._close_lookup：每次组合模拟都为所有币的所有分钟建 Python dict（数千万个条目），耗时且占大量内存。
  3. scripts/backtest.py 一次运行会调用约 40 次 run_backtest：reference/user × 3 情景、breakeven 二分每个运行约 12 次、
     sizing_sweep 4 次、S4 2 次……每次都从头重算全部币的预计算和上面的盯市曲线。
  4. scripts/tuning_exits.py 每组出场参数扫 26 个 θ，每个 θ 都跑一次完整组合模拟（含第 1 点）。
  5. engine.precompute_trades 与 labels.exit_sim 逐信号 Python 循环，每个信号调用一次 compute_entry 和 numba simulate_exit
     （30 个参数的调用开销），构造 dataclass；S1 随机基准对全部预过滤样本做同样计算。
  6. features.normalize.ewm_standardize 是逐元素纯 Python 循环（约 30 个 ewm_z 特征 × 每币全部分钟）；
     tuning_exits.py 每次启动都重算全部特征；features.kline.wilder_atr 也是纯 Python 循环，且每次 run_backtest 都重算。
  7. common/_numba.py 用 cache=False，每个进程都要重新编译。

目标
- 在不改变任何回测结果的前提下，量化每个环节耗时，为后续优化（第 5~8 步）提供基准和“标准答案”快照。

范围与红线
- 只用调参期 M1~M12 的数据（不读测试段 M13~M22 的结果做任何判断，不读封存集 M23~M24），这是性能基准，不登记 EXPERIMENTS.log。
- 不修改 src/ 下任何计算逻辑。

步骤
1. 新建 scripts/bench_backtest.py：
   - 参数：--coins N（取调参期快照里按 alias 排序的前 N 个币，确定性）、--months（调参期内的月份范围，例如 2025-07:2025-09）、
     --signals r0（用 trade.backtest.r0 现场生成 R0 信号）、--suite {base,full}、--out artifacts/bench/{tag}/、--profile。
   - load_bars 的起点与正式回测一致（window_bounds 的 start_ms），终点为所选月份末；不得为了提速改变加载起点
     （Wilder ATR 是递推的，起点不同数值会变）。
   - suite=base：只跑 reference/base 一次 run_backtest。
   - suite=full：按 scripts/backtest.py 的同样顺序跑 2 个运行 × 3 情景、breakeven、sizing_sweep、S1、S4（直接调用相同函数，不复制逻辑）。
   - 用 time.perf_counter 记录每个阶段耗时：加载 bars、R0 信号、每次 precompute、每次 simulate_portfolio（拆出 _close_lookup 与
     _mark_to_market_curve 两项）、breakeven、sweep、S1、S4；输出 timing.json。
   - 记录进程峰值内存（Windows 下用 psutil；若未安装则记“未测”并在报告说明，不新增依赖）。
   - --profile 时用 cProfile 输出累计耗时前 30 的函数到 profile.txt。
2. 结果快照（后续优化的“标准答案”）：把每个 (run, scenario) 的 trades、skipped、equity_curve 写成 parquet，
   metrics、breakeven 滑点、sweep 表、S1、S4 结果写成 json，放在 --out 目录。
3. 新建 scripts/bench_compare.py <基准目录> <新结果目录>：逐文件比较；整数、字符串字段完全一致；浮点字段 rtol=1e-12、atol=1e-9；
   行数不同或任一字段超差即非零退出，并打印前 20 处差异。
4. 规模测试：依次运行 (coins, months) = (2, 1)、(5, 1)、(5, 2)、(10, 1)，suite=full，记录总耗时与各阶段耗时，
   用这 4 组数据说明各阶段随“交易笔数”“币数”“月数”的增长关系（线性还是平方）。不要直接跑使用者的三个月全量。

    月 300 笔（10 笔/日）：约 6bp，毛优势约 15~18bp
